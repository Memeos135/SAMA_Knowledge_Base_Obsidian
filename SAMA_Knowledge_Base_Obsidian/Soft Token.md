# Soft Token

## Connections

### [[Hard Token]] — `references` [EXTRACTED]
- **What this link tells you:** When interpreting the Framework's authentication terms, read hard token and soft token as the paired hardware/software alternatives that the glossary explicitly cross-references, both feeding the same MFA obligation. The hard-token entry directs 'See also Soft token', and the e-banking controls treat them jointly ('hard and soft tokens should be password protected'). You would conclude the two are interchangeable factor types for compliance purposes, so choosing one over the other does not change the underlying MFA and password-protection requirements you must satisfy.

- **What this link tells you:** When evaluating MFA implementations, recognise that the Framework expressly contemplates soft tokens (alongside hard tokens) as an acceptable authentication factor, but subjects them to the same protection requirements. The e-banking control considerations state that 'the use of hard and soft tokens should be password protected', linking the soft-token concept directly to the MFA obligation. You would conclude that a soft-token-based MFA is permissible, but must be password-protected and combined with a second factor to meet the mandate — a bare soft token does not by itself satisfy the requirement.
