# Detect Domain

## Connections

### [[Counter-Fraud Framework]] — `references` [EXTRACTED]
- **What this link tells you:** When mapping which control requirements bind a Member Organisation, recognise that 'Detect' is one of the four mandated domains structuring the Counter-Fraud Framework, carrying its own Principle and Control Requirements. The Framework obliges organisations to define, approve, implement and maintain fraud detection standards aligned to their Fraud Risk Assessment, addressing both internal and external fraud. Conclude that detection obligations are enforceable framework requirements, not optional add-ons, and check the Detect domain's specific control requirements when assessing coverage of fraud identification duties.
- **Grounding — this node (Page 45 / 5.1 Fraud Detection Standards):** "Member Organisations should have defined, approved, implemented and maintained fraud detection standards which should be aligned to the fraud risks..."
- **Grounding — related node (Page 9 / 2.1 Structure):** "The Framework is structured around four main domains, namely: Governance, Prevent, Detect, Respond."

### [[Fraud Detection Systems]] — `references` [EXTRACTED]
- **What this link tells you:** When assessing detection obligations, read Fraud Detection Systems as the technology/control specifics mandated within the Detect domain (Section 5), not a discretionary add-on. The Detect domain requires defined, approved and maintained fraud detection standards, and control requirement (g) states those standards 'should include at a minimum' the data sources, controls, and systems/technology used to detect fraud. The consequence: a reviewer should confirm detection systems are documented within the detection standards and justified against the Fraud Risk Assessment, and should not accept detection tooling that lacks the stated rationale and minimum content.
- **Grounding — this node (Page 45 / Section 5.1):** "Member Organisations should have defined, approved, implemented and maintained fraud detection standards which should be aligned to the fraud risks impacting the organisation and its customers."
- **Grounding — related node (Page 46 / 5.1(g)):** "Systems and technology implemented to detect potential fraud (e.g., fraud detection software, alerts on high-value events or transactions, access monitoring, link analysis)."

### [[Whistle Blowing Process]] — `references` [EXTRACTED]
- **What this link tells you:** When mapping detection obligations, note that the Whistle Blowing process (5.4) is a sub-domain of the Detect domain and functions as a human detection channel, distinct from automated monitoring. The Framework requires a whistle blowing process across multiple channels for employees and third parties, and cross-references an external instrument: it 'should comply with SAMA's Whistle Blowing Policy for Financial Institutions.' The consequence: a compliance reviewer must check conformity not only with this Framework but also with the separate Whistle Blowing Policy, and confirm the good-faith no-retaliation protection is in place.
- **Grounding — this node (Page 45 / Section 5):** "Fraud detection systems and controls are risk-based measures to identify fraud by looking for indicators in customer behaviours, transactional and non-transactional information."
- **Grounding — related node (Page 50 / Section 5.4):** "The process should comply with SAMA's Whistle Blowing Policy for Financial Institutions (Whistle Blowing Policy)."
